\chapter{Grundlagen}

Dieses Kapitel fasst die Konzepte zusammen, auf denen das System aufbaut.
Es ist ein Entwurf und wird mit den Phasen präzisiert.

\section{Datenmodell}

Git speichert Inhalte als Objekte, die über ihren Hash adressiert werden.
Es gibt drei Grundtypen: Blobs für Dateiinhalte, Trees für Verzeichnisse und Commits für
Snapshots mit Verweis auf Vorgänger. Der Verlauf bildet damit einen azyklischen Graphen aus
unveränderlichen Knoten. Dieser Aufbau ist die Stärke des Modells, weil identische Inhalte nur
einmal gespeichert werden und Änderungen nachträglich nicht unbemerkt verändert werden können
(\in{Abbildung}[fig:objects]).

Stemma übernimmt dieses Modell und ändert vier Dinge. Die ID eines Objekts trägt den Algorithmus
als Präfix (\type{b3:} für BLAKE3), damit später ein anderer Hash möglich bleibt.
Jeder Commit trägt eine Change-ID (\type{ch:} und 32 Hexziffern),
die bei jedem Umschreiben derselben Änderung gleich bleibt,
damit ein Review oder ein Rebase \quotation{dieselbe Änderung} wiederfindet.
Sie ist zufällig und wird nicht aus dem Inhalt abgeleitet.
Jeder Commit nennt einen Akteur, einen Menschen oder einen Agenten mit Modell, Session und Sponsor.
Einen Committer gibt es nicht. Die Leser sind streng: Was die Kodierung nicht geschrieben hätte,
wird abgelehnt, damit jedes Objekt genau eine Kodierung und eine ID hat.

\section{Referenzen}

Branches und Tags sind Zeiger auf Commits. HEAD zeigt auf den aktuellen Branch.
Diese Trennung zwischen unveränderlichen Objekten und veränderlichen Zeigern ist für das Projekt
wichtig: Schreibhoheit betrifft die Zeiger, nicht die Objekte.

\section{Arbeitskopie und Index}

Git trennt drei Zustände: die Arbeitskopie, den Index als Staging-Bereich und den letzten Commit.
Der Index ist eine Zwischenstufe, die Entwicklerinnen und Entwickler bewusst füllen.
Für Agenten ist diese Stufe eine Fehlerquelle, wenn unvollständige Zustände committet werden.
Ein anderer Ansatz betrachtet die Arbeitskopie selbst als Commit, wie es Jujutsu tut \cite[jujutsu].
Stemma folgt ihm (ADR-010): Bei jedem Befehl wird das Arbeitsverzeichnis als Commit gesichert,
sodass der Zustand eines Agenten nicht verloren geht, auch wenn er nichts bestätigt hat.
Die Change-ID überdauert dabei jeden neuen Snapshot derselben Änderung.
Ein Merge-Commit führt zwei Änderungen zusammen und bekommt eine neue.
Neue Dateien kommen erst in den Verlauf, wenn ein Befehl sie bestätigt, und eine Ausschlussdatei
hält Pfade wie Build-Ausgaben und Geheimnisse heraus. Zwischen zwei Aufrufen kann Stemma nichts
sichern, einen Dateiwächter gibt es in Phase 1 nicht.

\section{Konflikte und Operation Log}

Git bricht einen Vorgang ab, wenn ein Konflikt entsteht.
Jujutsu speichert Konflikte dagegen im Commit selbst \cite[jujutsu].
Ein Agent kann so weiterarbeiten und den Konflikt später lösen.
Ein Operation Log protokolliert jeden Schritt und ermöglicht das Zurücksetzen beliebiger
Operationen. Beide Ideen passen gut zu Agenten, die viele Schritte ausführen.

In Stemma ist das Log lokal und gehört nicht zum Verlauf (ADR-005, ADR-011).
Es hält fest, welche Zeiger eine Operation von welchem auf welchen Wert gesetzt hat, wer sie
ausgeführt hat und wann. Damit bleibt jeder ersetzte Commit erreichbar, auch der
Working-Copy-Commit, den ein Snapshot ablöst. Der Eintrag wird geschrieben, bevor der Zeiger sich
bewegt: Bricht ein Prozess dazwischen ab, steht der alte Commit schon im Log.
Jeder Eintrag ist eine eigene Datei mit fortlaufender Nummer, sodass mehrere Agenten gleichzeitig
schreiben können, ohne sich zu sperren, und ein einzelner Eintrag sich ersetzen lässt, wenn ein
Geheimnis entfernt werden muss.

\section{Ideen aus anderen Systemen}

\startitemize
\item {\bf Jujutsu (jj):} Stabile Change-IDs, Konflikte als Daten,
Operation Log und Git als Speicher \cite[jujutsu].
\item {\bf Pijul:} Ein Modell auf Basis von Patches statt Snapshots.
Es zeigt eine andere Grundannahme \cite[pijul].
\item {\bf Sapling:} Ein System für grosse Monorepos mit Fokus auf Skalierung \cite[sapling].
\item {\bf Scion (Anthropic):} Laut dem Engineering-Blog von Anthropic
\cite[anthropic2026redesigning] ein zentrales System, in dem der Server jeden Commit und jeden
Merge ausführt.
Einen vollständigen lokalen Klon gibt es nicht;
viele Jobs kommen ganz ohne Arbeitskopie aus und arbeiten über die API.
Der Beitrag nennt keine öffentliche Verfügbarkeit, und das Projekt übernimmt keinen Code.
Stemma teilt mit Scion die inhaltsadressierten Daten und übernimmt die API-Parität und die Idee
der abgeleiteten Daten.
Es bleibt aber ein lokales System mit vollständigem Klon und zielt auf kleine Teams,
nicht auf ein Monorepo (ADR-015).
\stopitemize

Das Projekt nutzt diese Systeme als Ideengeber. Text und Code entstehen neu.
