\chapter{Phase 1: Lokaler Kern}

\section{Ziel}

Ein lokales Repository mit einer Arbeitskopie, in der ein Akteur arbeitet, Mensch oder Agent.
Es lässt sich anlegen, Dateien werden verfolgt und gespeichert, Commits erzeugt
und der Status angezeigt.
Jede Zeigerbewegung steht im Operation Log und lässt sich zurücksetzen,
und ein Geheimnis lässt sich aus Verlauf und Log entfernen.

\section{Umfang}

\startitemize
\item Objektspeicher mit Blobs, Trees und Commits, adressiert über BLAKE3 mit Präfix nach ADR-001.
\item Referenzen für den Branch \type{main} und HEAD.
\item Suche des Repositories aus einem Unterverzeichnis (ADR-009).
\item Arbeitskopie als Commit mit Change-IDs (ADR-010): \type{commit}, \type{status},
\type{op restore} und \type{purge --apply} halten das Verzeichnis zuerst in einem Snapshot fest,
\type{track} speichert die verfolgten Dateien mit.
\item Befehle \type{init}, \type{track} (statt \type{add}), \type{commit}, \type{status},
\type{op log}, \type{op restore}, \type{op verify} und \type{purge}.
\item Ausschlussdatei \type{.stemmaignore} (ADR-012).
\item Akteur-Felder in jedem Commit und im Operation Log nach ADR-002.
\item Operation Log als Verzeichnis nummerierter Einträge, die vor jeder Änderung eines
Zeigers geschrieben werden (ADR-011).
\item Hash-Kette über das Log mit einem Anker für \type{op verify --anchor} (ADR-011).
\item Purge über ein Journal mit \type{--resume} und \type{--abort} (ADR-014).
\stopitemize

\section{Aufbau eines Repositories}

Ein Repository ist ein Verzeichnis, das einen Ordner \type{.stemma} enthält.
Die Schicht \type{Repository} in \type{stemma-core} bündelt Objektspeicher, Referenzen und Log,
damit jede Operation die Speicher desselben Repositories verwendet (ADR-009).
Ein Befehl findet sein Repository auch aus einem Unterverzeichnis:
Er nimmt das Repository im Startverzeichnis oder sonst das nächste darüber, wie Git
(\type{Repository::discover}).

Ein \type{.stemma}, das die Suche findet, muss dem Konto gehören, unter dem der Befehl läuft,
damit niemand mit einem \type{.stemma} in einem geteilten Verzeichnis die Befehle
anderer abfängt. Unter Unix gilt das auch für ein \type{.stemma} im Startverzeichnis,
denn \type{-C} ist ohne Angabe das aktuelle Verzeichnis: Nach \type{cd /tmp} öffnet ein
Befehl kein \type{/tmp/.stemma} eines anderen Kontos.
Unter Windows, wo die Standardbibliothek von Rust keinen Besitzer liefert,
wird nur ein \type{.stemma} oberhalb im Wurzelverzeichnis eines Laufwerks abgelehnt.
Die Prüfung ist nicht frei von Wettläufen (ADR-009).

\starttyping
.stemma/
    format        stemma-repository 4 (2 oder 3 vor der Hash-Kette)
    HEAD          branch main
    working-copy  ID des Working-Copy-Commits
    objects/      lose Objekte
    oplog/        Operation Log, eine nummerierte Datei je Eintrag
    oplog-tip     Nummer und Hash des letzten Eintrags des Logs
    refs/heads/   Branches
    refs.lock     Sperre der Referenzen, solange ein Befehl schreibt
    refs.lock.guard  Datei für die Sperre des Betriebssystems, bleibt
    purge-pending Journal eines Purge, nur solange er läuft oder nachdem er abbrach
    tmp/          temporäre Dateien des Objektspeichers, der Referenzen und des Logs
\stoptyping

Die Datei \type{format} trägt eine Versionsnummer. \type{init} schreibt die Version 4,
die das Log mit der Hash-Kette kennzeichnet (siehe unten). Ein Repository der Version 2 oder 3
steigt mit seinem nächsten Eintrag im Log auf 4. Beim Öffnen nimmt der Kern die Versionen 2
bis 4 an und lehnt eine fehlende, eine nicht kanonische und jede andere Version ab, auch die
Version 1 der Repositories ohne Log. Eine Version sinkt nie.
Ein älteres Programm weist damit ein neueres Repository zurück, statt es zu beschädigen.

\type{init} legt ein Repository so an, dass nie ein halbes entsteht
(\type{Repository::init}):

\startitemize[n]
\item Es ruft \type{authorize} mit dem Akteur auf,
wie jede Operation, die ein Repository ändert.
\item Es baut den Ordner unter einem temporären Namen neben \type{.stemma} auf.
\item Es schreibt \type{format}, HEAD, den ersten Working-Copy-Commit und den ersten Eintrag
des Logs.
\item Es schreibt alle neuen Dateien und Ordner auf den Datenträger.
\item Es benennt den Ordner in \type{.stemma} um und sichert das Verzeichnis darüber.
\stopitemize

HEAD zeigt auf den Branch, standardmässig \type{main} (Option \type{--initial-branch});
der Branch selbst entsteht erst mit dem ersten Commit.
Die Arbeitskopie ist von Anfang an ein Commit (ADR-010):
Der erste Working-Copy-Commit hat den leeren Baum, keine Eltern und eine eigene Change-ID,
und die Datei \type{working-copy} hält seine ID fest.
Existiert \type{.stemma} bereits, bricht \type{init} ab und ändert nichts.
Ein Fehler entfernt den temporären Ordner wieder; gelingt auch das Entfernen nicht,
nennt die Fehlermeldung den Ordner.
Ein leeres \type{.stemma}, das ein anderer Prozess zwischen Prüfung und Umbenennung anlegt,
ersetzt \type{init} unter Unix noch (offener Punkt in ADR-009).

Ein Zeiger kann nur auf einen Commit gesetzt werden, der im Objektspeicher liegt (ADR-008).
Nennt ein Zeiger später doch keinen gültigen Commit, etwa weil jemand eine Objektdatei entfernt
oder eine Referenzdatei von Hand geändert hat, findet das die Prüfung der Referenzen
(\type{Repository::verify_refs}).
Sie prüft einen abgekoppelten HEAD, den Working-Copy-Commit und jeden Branch.
Sie meldet jeden Zeiger, dessen Commit fehlt, beschädigt ist oder sich nicht lesen lässt,
und jeden, der auf ein Objekt anderer Art zeigt, etwa auf einen Baum.

\startinfobox
{\bf Grenzfälle der Prüfung der Referenzen.}
\startitemize
\item Die Prüfung ist flach: Der Commit wird gelesen und sein Hash geprüft,
aber weder geparst, noch werden sein Baum und seine Eltern verfolgt.
\item Ein HEAD, der einen noch nicht angelegten Branch nennt, ist kein Fehler.
\item Eine Referenzdatei, die fehlt oder nicht in kanonischer Form ist,
beendet die Prüfung mit ihrem Fehler.
\item Die Prüfung liest ohne Sperre. Einen Zeiger, der durchfällt, liest sie ein zweites Mal
und prüft ihn an seinem neuen Commit, falls er sich bewegt hat.
Ein Purge, der während der Prüfung einen Zeiger versetzt und den alten Commit löscht,
erzeugt so keinen Befund.
Ein Branch, den eine andere Änderung während der Prüfung löscht, ist ebenfalls kein Befund.
\item Eine Datei oder ein Verzeichnis unter \type{refs/heads}, deren Name kein Branch-Name ist,
bleibt ein Schaden und beendet die Prüfung, etwa die Sicherung \type{main~} eines Editors;
die Meldung nennt den Pfad. Namen, die mit einem Punkt beginnen, wie \type{.DS_Store},
werden übersprungen.
\item Besteht das Journal eines Purge vor oder nach der Prüfung, lehnt sie ab.
\stopitemize
\stopinfobox

\section[sec:object-ids]{Objekte und ihre IDs}

Alles, was Stemma vom Inhalt eines Repositories speichert, ist ein Objekt:
ein Blob für den Inhalt einer Datei, ein Baum für ein Verzeichnis
und ein Commit für einen gespeicherten Stand (\in{Abbildung}[fig:objects]).
Ein Objekt wird über einen Hash seines Inhalts adressiert, nicht über einen Namen.
Daraus folgen die Eigenschaften, auf denen die übrigen Abschnitte aufbauen:
Gleiches wird einmal gespeichert, eine Änderung fällt beim Lesen auf,
und eine einzige ID legt einen ganzen Stand fest.
Dieser Abschnitt definiert die Struktur, nennt ihre Invarianten und ihre Kosten
und begründet, warum die Garantien gelten.

\subsection{Inhaltsadressierung}

Ein Objekt besteht aus einer Art, \type{blob}, \type{tree} oder \type{commit},
und einem Rumpf aus Bytes. Seine ID ist der BLAKE3-Hash über einen Kopf und den Rumpf
\cite[oconnor2020blake3], mit dem Algorithmus als Präfix (ADR-001):

\starttyping
ID = "b3:" + hex( BLAKE3( "<Art> <Länge des Rumpfs>" + NUL + Rumpf ) )
\stoptyping

Die Länge steht dezimal und ohne führende Nullen. Weil die Art zum gehashten Kopf gehört,
erhalten gleiche Bytes als Blob und als Baum verschiedene IDs (\type{hash_encoding}).
Der Speicher legt ein Objekt als Datei unter \type{objects/b3/} ab,
in einem Verzeichnis aus den ersten zwei der 64 Hexziffern
und unter dem Namen aus den übrigen 62 (\type{object_path}).
Die Datei enthält Kopf und Rumpf unkomprimiert.
Die zwei Ziffern verteilen die Objekte auf höchstens 256 Verzeichnisse,
so dass kein einzelnes Verzeichnis alle Objekte hält.

Für den Speicher gilt eine Invariante:
{\em Die Bytes unter einer ID hashen auf diese ID.}
Der Speicher prüft sie bei jedem Lesen eines Objekts. Er liest die Datei,
verlangt genau den Kopf, den Art und Länge ergeben, hasht und vergleicht.
Ein Objekt, das die Prüfung nicht besteht, meldet er als beschädigt
und gibt es nie weiter (\type{read_checked}).
Beim Schreiben berechnet er die ID zuerst.
Liegt unter ihr schon ein unversehrtes Objekt, schreibt er nichts;
gleicher Inhalt liegt so nur einmal im Speicher.
Ein beschädigtes Objekt ersetzt er unter Unix durch das neue;
auf anderen Systemen, und wenn statt einer Datei etwa ein Verzeichnis im Weg liegt,
meldet er den Schaden.

\subsection{Der Merkle-Graph}

Ein Baum kodiert je Eintrag eine Zeile \type{<Modus> <Name>} und eine Zeile mit der ID,
nach Namen in der Bytefolge von UTF-8 sortiert und ohne doppelten Namen (\type{Tree::new}).
Ein Commit nennt seinen Baum und seine Eltern ebenfalls über deren IDs.
Die ID eines Objekts hängt damit von den IDs aller Objekte ab, die es erreicht:
Die Objekte bilden einen Merkle-Graphen \cite[merkle1987].
Gleiche IDs bedeuten deshalb gleiche Teilgraphen, so dass ein Vergleich zwei gleiche Verzeichnisse
überspringen kann, ohne sie zu lesen.
Eine Änderung an einer Datei ändert dagegen die ID jedes Baums darüber und die des Commits,
so dass die ID eines Commits den ganzen Stand festlegt.

Zum Graphen gehören weitere Invarianten.
{\em Jedes Objekt hat genau eine Kodierung.}
Die strengen Leser nehmen nur die kanonische Form an:
sortierte Einträge, einen kanonischen Kopf, keine überzähligen Zeichen (ADR-005).
Hätte derselbe Baum zwei Kodierungen, hätte er zwei IDs;
gleicher Inhalt läge doppelt im Speicher, und der Vergleich fände Unterschiede, wo keine sind.
{\em Der Graph hat keinen Kreis}; er ist ein gerichteter azyklischer Graph
\cite[sedgewick2011algorithms] (Abschnitt 4.2).
Stemma prüft das nicht; es folgt aus der Konstruktion (\in{Abschnitt}[sec:object-guarantees]).

\subsection{Die Ordnung der Pfade}

Der Snapshot sammelt die verfolgten Dateien in einer geordneten Symboltabelle
(\type{Index}, eine \type{BTreeMap}; trotz des Namens kein Staging-Bereich wie bei Git)
und baut daraus die Bäume.
Die Tabelle ordnet zwei Pfade Komponente für Komponente:
Sie zerlegt beide an \type{/}, vergleicht die Teile in der Bytefolge von UTF-8,
und ein Pfad, der Anfang eines anderen ist, kommt zuerst (\type{compare_paths}).
Diese Ordnung ist die Reihenfolge, in der eine Tiefensuche durch die sortierten Bäume
die Dateien besucht \cite[sedgewick2011algorithms] (Abschnitt 4.1).
Die Bytefolge der ganzen Zeichenkette ist es nicht:
Da \type{.} vor \type{/} kommt, stünde \type{a.b} vor \type{a/b},
während die Tiefensuche das Verzeichnis \type{a} vor der Datei \type{a.b} vollständig besucht.
Anders als Git ordnet Stemma ein Verzeichnis im Baum nach seinem Namen allein,
ohne angehängten Schrägstrich.

Weil die Tabelle in dieser Ordnung durchlaufen wird, stehen die Dateien eines Verzeichnisses
hintereinander, und ein Verzeichnis ist vollständig, sobald der Durchlauf es verlässt.
Das Schreiben der Bäume nutzt das in einem einzigen Durchlauf
mit einem Stapel offener Verzeichnisse (\type{write_tree}):

\startitemize[n]
\item Für jeden Pfad schliesst es die offenen Verzeichnisse, die der Pfad nicht mehr teilt,
vom innersten nach aussen. Ein Verzeichnis zu schliessen heisst, seinen Baum zu schreiben
und ihn als Eintrag in das Verzeichnis darüber aufzunehmen.
\item Es öffnet die Verzeichnisse des Pfads, die noch nicht offen sind.
\item Es fügt die Datei als Eintrag in das innerste offene Verzeichnis ein.
\item Am Ende schliesst es alle offenen Verzeichnisse und schreibt den Wurzelbaum.
\stopitemize

Jeder Baum wird genau einmal geschrieben, nach allen Bäumen unter ihm, also in Postorder.
Der Stapel hält nie mehr Verzeichnisse, als der tiefste Pfad Ebenen hat,
und eine Schleife ersetzt die Rekursion, so dass ein tiefer Baum den Aufrufstapel nicht erschöpft.

Der Snapshot liest jede unveränderte Datei dreimal:
aus dem Arbeitsverzeichnis, als gespeichertes Objekt, wenn das Schreiben prüft,
ob es schon unversehrt vorliegt, und noch einmal, wenn der Kern vor dem Schreiben
der Bäume jeden Blob prüft (\type{Index::verify}).
Eine Datei, deren Inhalt neu ist, liest er zweimal und schreibt sie einmal.
Das ändert die Ordnung $O(S)$ nicht, wohl aber die Konstante;
einen Cache, der unveränderte Dateien erkennt, gibt es noch nicht.
Der Vergleich zweier Bäume für \type{status} liest beide Seiten Verzeichnis für Verzeichnis.
Zwei Verzeichnisse mit gleicher ID überspringt er, ohne sie zu lesen.
Zwei Verzeichnisse mit verschiedener ID durchläuft er nebeneinander
wie den Mischschritt beim Sortieren durch Mischen,
in einer Zeit, die linear in der Zahl ihrer Einträge ist
\cite[sedgewick2011algorithms] (Abschnitt 2.2).
Gelesen werden die Wurzel und höchstens die Verzeichnisse auf den Wegen
zu den $k$ Unterschieden;
ein ganz neues oder ganz entferntes Verzeichnis liest er vollständig,
doch jede Datei darin zählt zu den $k$.

\subsection[sec:object-guarantees]{Warum die Garantien gelten}

Alle Garantien des Objektspeichers stützen sich auf eine Annahme:
Niemand kann zwei verschiedene Eingaben mit demselben BLAKE3-Hash finden
(Kollisionsresistenz). Für einen Hash von 256 Bit braucht ein allgemeiner Angriff
auf diese Eigenschaft in der Grössenordnung von $2^{128}$ Versuchen \cite[oconnor2020blake3].

Gleiche ID bedeutet gleicher Inhalt; sonst wären zwei Kodierungen mit gleichem Hash gefunden.
Darauf beruhen das einmalige Speichern und das Überspringen gleicher Verzeichnisse.
Eine Änderung an gespeicherten Bytes fällt beim nächsten Lesen auf,
denn sie bricht die Invariante des Speichers.
Erkannt heisst nicht verhindert: Ein beschädigtes Objekt bleibt beschädigt,
bis unter Unix ein Snapshot denselben Inhalt wieder speichert;
anderswo bricht das Speichern mit dem Fehler ab.
Ein fehlendes Objekt bringt Stemma nicht zurück.

Ein Kreis im Graphen verlangt ein Objekt, dessen Kodierung über eine Kette von Objekten
die eigene ID enthält. Die ID ist aber der Hash eben dieser Kodierung.
Wer einen Kreis bauen will, muss also eine Eingabe finden,
deren Hash, über die Kette weitergereicht, in ihr selbst vorkommt.
Verhält sich BLAKE3 wie eine Zufallsfunktion, gelingt das nur mit einer Zahl von Versuchen
in der Grössenordnung von $2^{256}$. Ein Durchlauf durch den Graphen,
etwa beim Vergleich oder beim Purge, kommt deshalb immer zu einem Ende.

Ein Absturz während des Schreibens lässt den Speicher in einem gültigen Zustand.
Ein Objekt entsteht als temporäre Datei unter \type{tmp/}, wird gesichert
und dann an seinen Pfad umbenannt; danach wird sein Verzeichnis gesichert (ADR-007).
Unter dem Pfad liegt also entweder nichts oder das vollständige Objekt.
Was unter \type{tmp/} liegen bleibt, räumt der nächste Befehl auf, der die Sperre nimmt.
Ein Objekt, das kein Zeiger erreicht, ist harmlos; es kostet nur Platz.
Die Reihenfolge der Schritte in \in{Abschnitt}[sec:pointer-move] sorgt dafür,
dass die Objekte gesichert sind, bevor ein Eintrag im Log oder ein Zeiger sie nennt.

\section{Arbeitskopie und Commits}

Die Arbeitskopie ist in Stemma selbst ein Commit, der Working-Copy-Commit (ADR-010).
Einen Index wie bei Git gibt es nicht:
Verfolgt sind genau die Dateien, die im Baum des Working-Copy-Commits stehen.
Die Befehle, die den Stand der Arbeitskopie brauchen,
halten das Arbeitsverzeichnis vor ihrer eigenen Arbeit in diesem Commit fest.
Eine kurze Sitzung begleitet die folgenden Abschnitte;
die Ausgaben stammen aus einem echten Lauf, nur die IDs sind gekürzt.

\subsection{Der Akteur eines Befehls}

Jeder Befehl, der schreibt, braucht einen Akteur.
Die Kommandozeile liest ihn aus der Option \type{--actor}
oder aus der Umgebungsvariablen \type{STEMMA_ACTOR}.
Der Text hat die Form der Akteur-Zeile eines Commits,
also \type{human daniel} oder \type{agent claude model=opus-5-5 session=s1 sponsor=daniel}.
Ohne Akteur bricht der Befehl ab und legt nichts an.
Einen Standardwert aus dem Namen des Kontos gibt es bewusst nicht,
damit ein Agent nie stillschweigend als Mensch auftritt.
Modell und Session halten fest, welche Version eines Agenten in welchem Lauf gehandelt hat;
der Sponsor ist der Mensch, der für den Agenten einsteht (ADR-002).

\startinfobox
{\bf Grenzfälle des Akteurs.}
\startitemize
\item Die Option geht der Variablen vor.
\item Ein leerer Wert gilt als Fehler und fällt nicht auf die Variable zurück.
\stopitemize
\stopinfobox

Die Sitzung beginnt mit einem neuen Repository und zwei Dateien:

\starttyping
$ export STEMMA_ACTOR="human daniel"
$ stemma init
Initialized empty Stemma repository in /home/daniel/notizen/.stemma
$ echo "Hallo" > README.md
$ mkdir src && echo "fn main() {}" > src/main.rs
\stoptyping

\subsection{Der Snapshot}

Ein Snapshot hält den Stand des Arbeitsverzeichnisses im Working-Copy-Commit fest
(\type{Repository::snapshot}, ADR-010).
Die Befehle \type{commit}, \type{status}, \type{op restore} und \type{purge --apply}
machen ihn, bevor sie ihre eigene Arbeit tun;
\type{track} speichert die verfolgten Dateien in derselben Operation mit.
Eine Änderung an einer verfolgten Datei landet so im Verlauf,
ohne dass jemand sie eigens vormerken muss.

Ein Snapshot läuft in diesen Schritten ab:

\startitemize[n]
\item Der Kern prüft, ob der Akteur den Snapshot machen darf (\type{authorize}).
\item Er nimmt die Sperre der Referenzen.
\item Er liest den Baum des Working-Copy-Commits.
\item Aus dem Arbeitsverzeichnis liest er genau die Dateien, die in diesem Baum stehen.
Eine Datei ausserhalb des Baums ist nicht verfolgt;
er speichert sie nicht und meldet sie nicht.
\item Eine geänderte Datei speichert er, eine gelöschte verlässt den Baum.
\item Er baut einen neuen Commit mit dem neuen Baum.
Der Commit behält Eltern, Change-ID und Nachricht des alten,
sein Autor ist der Akteur des Snapshots und seine Zeit die des Aufrufs.
Alle neuen Objekte schreibt er zuerst ungesichert nach \type{tmp/}
und sichert sie gemeinsam, bevor ein Eintrag oder ein Zeiger sie nennt (ADR-007).
\item Er schreibt den Eintrag und bewegt dann den Zeiger des Working-Copy-Commits.
\in{Abbildung}[fig:oplog-write] zeigt diese Schritte mit ihren Absturzpunkten.
\stopitemize

Ist der Baum unverändert, entstehen weder Commit noch Eintrag.
Ein Absturz, bevor die Objekte gesichert sind, verliert nur sie;
ihre Dateien in \type{tmp/} räumt der nächste Schreiber weg.
Ein Absturz danach und vor dem Eintrag lässt Objekte zurück, die nichts nennt;
sie schaden nicht.
Weil die Objekte gemeinsam gesichert werden,
wird jedes Verzeichnis unter \type{objects/} einmal gesichert statt einmal je Objekt.
Das erste \type{track} von 10'000 Dateien zu 1 KiB dauerte dadurch 49 statt 97 Sekunden
(\type{scripts/measure-track.sh}, Release-Build, macOS mit APFS auf einer SSD, ein Lauf;
ADR-007).

Ein Snapshot speichert, was im Verzeichnis liegt, und trägt den Akteur des Befehls ein.
Arbeiten zwei Akteure im selben Verzeichnis,
kann der Befehl des einen die Änderung des anderen speichern,
und das Log nennt dann nicht den Akteur, der die Änderung gemacht hat.
Deshalb gilt die Regel: Jeder Akteur arbeitet in einer eigenen Arbeitskopie (ADR-010).
Zwei Akteure in einem Verzeichnis sind kein unterstützter Betrieb.
Der Kern erzwingt das noch nicht, bis dahin gilt die Regel als Konvention;
die Durchsetzung kommt mit der zweiten Arbeitskopie (Worktree, Phase 3).

\startinfobox
{\bf Grenzfälle des Snapshots.}
\startitemize
\item Steht an der Stelle einer verfolgten Datei nun ein Verzeichnis,
verlässt die Datei den Baum wie eine gelöschte;
was in dem Verzeichnis liegt, bleibt unverfolgt.
\item Steht an der Stelle eines Verzeichnisses nun eine Datei oder ein Link,
verlassen die verfolgten Dateien darunter den Baum.
\item Ein Pfad wird nie über einen Link verfolgt.
Ein verfolgter Pfad, der selbst ein Link ist, wird als Link gespeichert:
mit dem Pfad, auf den er zeigt, nicht mit dem Inhalt des Ziels.
\item Unter Windows schreibt der Checkout einen Link als gewöhnliche Datei,
die das Ziel enthält, wie Git mit \type{core.symlinks=false}.
Der Snapshot liest eine solche Datei als Ziel und lässt den Pfad ein Link,
so dass ein Checkout mit folgendem Snapshot nichts ändert.
Anders als Git bricht der Snapshot ab, wenn die Datei kein Ziel enthält,
das ein Link unter Unix haben kann:
UTF-8, nicht leer, höchstens 4096 Bytes, ohne Nullbyte und ohne Zeilenumbruch.
Der Zeilenumbruch fängt auch einen Inhalt ab, der die Datei überschrieben hat,
als wäre sie das Ziel selbst;
zu einer gewöhnlichen Datei kann ein verfolgter Link unter Windows noch nicht werden.
\item Das Ausführbit gehört zum Dateimodus.
\item Eine verfolgte Spezialdatei (Gerät, Socket, Pipe) bricht den Snapshot mit einem Fehler ab,
statt still aus dem Verlauf zu fallen.
\item Jede verfolgte Datei wird ganz gelesen; eine unveränderte liest der Snapshot dreimal,
eine neue zweimal, und schreibt sie einmal (\in{Abschnitt}[sec:object-costs]).
Einen Cache gibt es noch nicht.
\stopitemize
\stopinfobox

\subsection{Dateien verfolgen}

Eine neue Datei kommt mit \type{track} in den Baum des Working-Copy-Commits.
Vorher zeigt \type{status} sie als unverfolgt (\type{?}):

\starttyping
$ stemma status
Untracked files:
? README.md
? src/main.rs
$ stemma track README.md src
tracked README.md
tracked src/main.rs
\stoptyping

Der Befehl nimmt Pfade relativ zu dem Verzeichnis, in dem er läuft (oder das \type{-C} nennt),
auch wenn das ein Unterverzeichnis des Repositories ist.
Ein Verzeichnis steht für die Dateien darunter, ohne einen Ordner \type{.stemma},
\type{.} allein für das Verzeichnis selbst;
\type{..} führt bis zur Wurzel des Repositories hinauf.
Die Kommandozeile bringt das, was eine Person tippt (\type{./a.txt}, \type{dir/}),
in diese Form;
ein leeres Argument lässt sie unverändert, damit der Kern es ablehnt (\type{normalize_path}).
Synopsis und Exit-Codes stehen in der Befehlsreferenz.

Der Kern baut den neuen Baum aus den verfolgten Dateien und den Dateien an den Pfaden
und ersetzt den Working-Copy-Commit wie ein Snapshot (\type{Repository::track}).
Die verfolgten Dateien speichert er mit, denn sonst ginge eine Änderung an ihnen verloren.
Ein Pfad, der schon verfolgt wird, ist kein Fehler,
solange kein Muster der Ausschlussdatei ihn ausschliesst.
Ein Pfad, den es nicht gibt oder der eine Pfadregel verletzt, wird abgelehnt,
bevor sich der Working-Copy-Commit bewegt.
Eine genannte Datei, die beim Speichern verschwunden ist, ist ebenfalls ein Fehler.

\startinfobox
{\bf Grenzfälle von \type{track}.}
\startitemize
\item Jeder Name im Pfad muss so geschrieben sein, wie ihn das Verzeichnis hat.
Ein Dateisystem ohne Unterscheidung von Gross- und Kleinschreibung nimmt sonst
\type{a.txt} für \type{A.txt}, und der Baum würde die Datei zweimal halten.
Der Fehler nennt die Schreibweise auf dem Datenträger.
\item Unter einem Verzeichnis überspringt der Befehl ohne Meldung die Namen,
die auf \type{.stemma} hinauslaufen,
und jede Datei und jedes Verzeichnis namens \type{.git} in jeder Tiefe (ADR-012).
Ebenso überspringt er eine Datei oder einen Link namens \type{.stemma-checkout-…},
den Rest eines unterbrochenen \type{op restore}:
Er enthält den Inhalt eines alten Blobs, vielleicht ein gepurgtes Geheimnis.
Ein genannter Pfad durch \type{.git} oder auf so einen Rest ist ein Fehler,
und \type{status} listet ihn, damit man ihn entfernt (ADR-013).
Jeder andere Name, den ein Baum ablehnt, bricht den Aufruf ab.
\stopitemize
\stopinfobox

\subsection{Die Ausschlussdatei}

Die Ausschlussdatei \type{.stemmaignore} liegt im Wurzelverzeichnis
und hält Dateien aus \type{track} und aus den unverfolgten Dateien von \type{status} heraus
(ADR-012, \type{ignore.rs}).
Eine Zeile ist ein Kommentar mit \type{#} oder ein Muster aus Teilen, die ein \type{/} trennt.
Ein Teil ist ein Name mit den Platzhaltern \type{*} (eine beliebige Folge von Zeichen
innerhalb eines Namens) und \type{?} (ein Zeichen),
oder ganz \type{**} (beliebig viele Verzeichnisse, auch keines).
Ein führendes oder ein mittleres \type{/} verankert das Muster an der Wurzel;
ohne eins trifft es einen Namen auf jeder Ebene.
Ein \type{/} am Ende trifft nur Verzeichnisse,
und ein getroffenes Verzeichnis schliesst alles darunter aus.

Ein Muster mit \type{**} prüft der Leser mit dynamischer Programmierung:
Eine Tabelle hat eine Zelle je Paar aus einem Teil des Musters und einem Teil des Pfads
(\type{parts_match}).
Ein Muster und ein Pfad brauchen damit höchstens das Produkt der beiden Längen,
mal den Aufwand für den Vergleich eines Namens;
weil der Leser auch jedes übergeordnete Verzeichnis des Pfads prüft,
kommt für einen ganzen Pfad ein Faktor seiner Länge hinzu.
Diesen Vergleich mit \type{*} und \type{?} macht ein Abgleich, der beim Scheitern nur zum
letzten \type{*} zurückgeht (\type{glob_matches});
auch er braucht höchstens das Produkt der Längen von Muster und Name.
Ein naiver rekursiver Abgleich kann bei mehreren \type{**} exponentiell viel Zeit brauchen;
hier lässt kein Muster die Zeit schneller als polynomiell wachsen.

Die Datei wird bei jedem Aufruf von \type{track} und \type{status} aus dem Verzeichnis gelesen,
nicht aus dem Baum.
Ist sie ungültig, ein Link oder keine gewöhnliche Datei, oder ändert sie sich beim Lesen,
bricht der Aufruf ab, bevor etwas verfolgt wird.
Ein Snapshot und \type{commit} lesen sie nie.
Was schon im Baum steht, bleibt verfolgt, und die Datei selbst schliesst kein Muster aus.

\startinfobox
{\bf Was der Leser der Ausschlussdatei ablehnt.}
\startitemize
\item Es gibt weder Negation noch Escape noch Zeichenklassen.
\type{!} am Anfang, \type{\}, \type{[} und \type{]} lehnt der Leser ab,
damit diese Formen später frei bleiben.
\item Der Leser ist streng wie die anderen:
UTF-8, jede Zeile endet mit einem Zeilenende,
keine Leerzeile, kein Leerzeichen am Rand, keine doppelte Zeile,
höchstens 1024 Byte je Zeile und 64 KiB je Datei.
Ein Fehler nennt die Zeile.
\item Gemischte Zeilenenden und ein \type{\r} ausserhalb von \type{\r\n} lehnt der Leser ab.
Ein Zeilenende ist \type{\n} oder \type{\r\n};
das zweite schreibt ein Editor unter Windows oder Git mit \type{autocrlf}.
Alle Zeilen einer Datei enden wie die erste,
sonst nennt der Fehler die erste abweichende Zeile.
\item Muster und Namen vergleicht der Leser Byte für Byte und mit Gross- und Kleinschreibung,
auch auf einem Dateisystem, das beides gleichsetzt.
Ein solcher Name bleibt dann unbemerkt verfolgt (offener Punkt in ADR-012).
\stopitemize
\stopinfobox

\subsection{Der Status}

Auch \type{status} macht einen Snapshot der verfolgten Dateien
(\type{Repository::status}, ADR-010).
Der Befehl braucht deshalb einen Akteur,
und ein Eintrag entsteht nur, wenn sich eine verfolgte Datei geändert hat.
Danach ist jede verfolgte Datei gleich dem Working-Copy-Commit,
\quotation{geändert} kann also nicht \quotation{anders als der Working-Copy-Commit} heissen.
Es heisst, wie bei Jujutsu: was der Working-Copy-Commit gegenüber seinem Elternteil tut.
Der Status läuft in diesen Schritten ab:

\startitemize[n]
\item Er liest die Ausschlussdatei und durchläuft das Arbeitsverzeichnis.
Bis hier ist nichts geschrieben.
\item Er macht einen Snapshot der verfolgten Dateien.
\item Er vergleicht den Baum des Working-Copy-Commits mit dem seines ersten Elternteils.
\item Er listet die unverfolgten Dateien und die Reste eines unterbrochenen Restore.
\stopitemize

Nach dem \type{track} der Sitzung hat der Working-Copy-Commit noch keinen Elternteil,
also gilt der leere Baum, und beide Dateien sind hinzugefügt:

\starttyping
$ stemma status
Working copy changes:
A README.md
A src/main.rs
\stoptyping

Die Ausgabe nennt hinzugefügte (\type{A}), geänderte (\type{M}) und gelöschte (\type{D})
Dateien, nach Pfad sortiert.
\type{M} gilt auch bei anderem Modus oder bei einem Link anstelle einer Datei.
Die Dateien eines hinzugefügten oder gelöschten Verzeichnisses stehen einzeln da.
Ein Wechsel von Datei zu Verzeichnis ist ein \type{D} und die \type{A} darunter,
sobald die Dateien darunter verfolgt sind;
vorher stehen sie unter den unverfolgten.
Bei mehreren Eltern gilt der erste.
Unverfolgt (\type{?}) sind die Dateien im Arbeitsverzeichnis,
die nicht im Baum des Working-Copy-Commits stehen
und die \type{.stemmaignore} nicht ausschliesst; auch sie stehen einzeln da.
Eine temporäre Datei, die ein unterbrochenes \type{op restore} zurückliess, steht in einem eigenen
Abschnitt (\type{!}), damit man sie entfernt (ADR-013).

\startinfobox
{\bf Grenzfälle von \type{status}.}
\startitemize
\item Beim Durchlaufen vor dem Snapshot bricht \type{status} dort ab, wo \type{track} abbricht:
bei einer ungültigen Ausschlussdatei, bei einem Namen, den ein Baum ablehnt
und den kein Muster ausschliesst, und bei einem Namen ohne UTF-8.
Dann hat es noch nichts geschrieben.
\item Scheitert das Lesen der Commits oder Bäume erst nach dem Snapshot, bleibt der Snapshot,
und der Fehler nennt seinen Eintrag.
\item Konnte der Snapshot den Zeiger bewegen, aber nicht sichern,
ist das ein Ergebnis mit einem Fehler und kein Abbruch, wie bei \type{commit}.
\item Die Zeiger liest \type{status} nacheinander und nicht unter der Sperre.
Bewegt ein anderer Prozess einen dazwischen, können HEAD und Commit aus zwei Zuständen stammen.
\item Ein Verzeichnis, das in beiden Bäumen dieselbe ID hat, liest der Vergleich nicht.
\stopitemize
\stopinfobox

\subsection{Der Commit}

Ein Commit benennt den Working-Copy-Commit und beginnt einen neuen (ADR-010).
Der benannte Commit wird Teil des Branches,
der neue nimmt die nächsten Änderungen auf (\type{Repository::commit}):

\starttyping
$ stemma commit -m "Erste Fassung"
Committed b3:2037…df79 on main
\stoptyping

Der Commit läuft in diesen Schritten ab:

\startitemize[n]
\item Der Kern lehnt eine leere Nachricht und einen HEAD ohne Branch ab
und prüft, ob der Akteur den Commit machen darf (\type{authorize}).
Bis hier ist nichts geschrieben.
\item Er nimmt die Sperre der Referenzen
und hält sie bis zur letzten Zeigerbewegung,
damit kein Purge dazwischen ein Objekt löscht, das der Commit nennt (ADR-014).
\item Er macht einen Snapshot,
damit eine Änderung seit dem letzten Befehl im Commit landet.
Das ist eine eigene Operation mit eigenem Eintrag.
\item Er prüft, dass der Branch beim Elternteil des Working-Copy-Commits steht
und dass sich der Baum gegenüber dem Elternteil geändert hat.
\item Der Working-Copy-Commit bekommt die Nachricht und den Akteur und die Zeit des Aufrufs;
Eltern, Baum und Change-ID behält er.
Weil sich sein Inhalt ändert, bekommt er eine neue ID.
\item Ein neuer Working-Copy-Commit entsteht als Kind des benannten:
mit demselben Baum, leerer Nachricht und eigener Change-ID.
\item Ein Eintrag nennt beide Zeigerbewegungen.
Der Branch rückt auf den benannten Commit,
danach der Zeiger des Working-Copy-Commits auf den neuen.
\stopitemize

Vor dem zweiten Commit hat die Sitzung \type{README.md} geändert.
Schon \type{status} hat die Änderung gespeichert, mit einem Eintrag \type{snapshot};
der Snapshot des Commits findet deshalb nichts mehr und schreibt keinen Eintrag.
\type{op log} zeigt den Eintrag des Commits mit beiden Zeigern:

\starttyping
$ echo "Hallo Welt" > README.md
$ stemma status
Working copy changes:
M README.md
$ stemma commit -m "Gruss erweitern"
Committed b3:9d8a…4c77 on main
$ stemma op log
5  2026-10-24T05:54:25Z  human daniel  commit
    working-copy  b3:7694…d054 -> b3:e394…b6eb
    branch main  b3:2037…df79 -> b3:9d8a…4c77
4  2026-10-24T05:54:23Z  human daniel  snapshot
    working-copy  b3:e6a3…109c -> b3:7694…d054
...
\stoptyping

\in{Abbildung}[fig:commit-pointers] zeigt die Zeiger vor und nach dem zweiten Commit der Sitzung.
Der neue Working-Copy-Commit ist leer, obwohl er einen Baum mit beiden Dateien hat:
Leer heisst, er hat denselben Baum wie sein Elternteil,
denn die verfolgten Dateien sind der Baum.

\startplacefigure[title={Zeiger vor und nach \type{commit}},
    reference=fig:commit-pointers,location=here]
\externalfigure[images/commit-pointers.pdf][width=0.9\textwidth]
\stopplacefigure

Scheitert der Commit nach dem Snapshot, aber vor dem Eintrag, bleibt nur der Snapshot;
die neuen Commits liegen ohne Zeiger im Objektspeicher.

\startinfobox
{\bf Wann ein Commit abgelehnt wird oder halb stehen bleibt.}
\startitemize
\item Ein unveränderter Baum
und ein Branch, der nicht beim Elternteil des Working-Copy-Commits steht,
lassen nur den Snapshot zurück.
Der zweite Fall wäre einer für einen Rebase (Phase 3).
\item Hat ein anderer Prozess einen Zeiger zuerst bewegt, scheitert der Commit;
er lässt sich wiederholen.
\item Bricht der Commit zwischen den beiden Zeigerbewegungen ab,
steht der Branch schon auf dem benannten Commit,
während der Working-Copy-Commit noch der alte ist (\type{PartlyMoved}).
Obwohl der Branch sich bewegt hat, nennt das Log den Eintrag dann nicht übernommen.
Der nächste \type{commit} erkennt den Zustand und beendet den ersten:
Er beginnt den neuen Working-Copy-Commit mit einem eigenen Eintrag
und verwendet die eigene Nachricht nicht.
\item Ob ein Commit abbrach, entscheidet das Log, nicht die Commits allein.
Stellt \type{op restore} einen Eintrag vor einem Commit wieder her,
erhält der Working-Copy-Commit eine ältere Fassung seiner selbst, und der Branch bleibt stehen.
Die Commits sehen dann aus wie nach einem Abbruch.
Das Log nennt den Eintrag des Commits aber übernommen,
also lehnt der nächste \type{commit} ab wie bei einem verschobenen Branch,
statt seine Nachricht stillschweigend zu verwerfen (ADR-010, ADR-013).
\stopitemize
\stopinfobox

\section{Das Operation Log}

Jede Operation, die einen Zeiger ändert, schreibt einen Eintrag in das Verzeichnis
\type{.stemma/oplog/} (ADR-011).
Ein Eintrag ist eine Textdatei, deren Name seine fortlaufende Nummer ist,
zwölf Ziffern mit führenden Nullen (\type{000000000001});
das Log hält damit höchstens 999'999'999'999 Einträge.
Ein Eintrag nennt den Akteur, die Zeit, den Namen der Operation
und für jeden geänderten Zeiger (HEAD, Working-Copy-Commit, Branches)
den alten und den neuen Wert:

\starttyping
stemma-oplog 3
number 1
time 1792435308
actor human daniel
previous -
operation init
head - branch:main
working-copy - b3:4feb…b32c
\stoptyping

Die Zeile \type{previous} gehört zur Hash-Kette, die weiter unten beschrieben ist.
Der Befehl \type{stemma op log} zeigt die Einträge,
und \type{stemma op restore} setzt die Zeiger auf die Werte vor einem Eintrag zurück
(siehe unten und die Befehlsreferenz).
\type{init} schreibt den ersten Eintrag.

\subsection[sec:pointer-move]{Ablauf einer Zeigerbewegung}

Der Eintrag entsteht vor der Zeigerbewegung.
Bricht ein Prozess dazwischen ab, steht der alte Wert schon im Log,
und der Commit, den der Zeiger vorher nannte, bleibt auffindbar.
\in{Abbildung}[fig:oplog-write] zeigt den Ablauf.
Ein Befehl, der schreibt, nimmt die Sperre der Referenzen, bevor er sein erstes Objekt speichert,
und hält sie bis zu seiner letzten Zeigerbewegung.
Unter der Sperre liest er den Zeiger und prüft die Änderung:
einen Namen, der nicht im Weg steht,
einen Branch, der dort steht, wo der Aufrufer ihn sah,
und einen Commit, der im Objektspeicher liegt.
Dann schreibt er den Eintrag, sichert ihn auf den Datenträger
und führt die Datei \type{oplog-tip} nach.
Erst danach bewegt er den Zeiger.

\startplacefigure[title={Ablauf einer Zeigerbewegung mit Absturzpunkten},
    reference=fig:oplog-write,location=here]
\externalfigure[images/oplog-write.pdf][width=0.9\textwidth]
\stopplacefigure

Weil nichts zwischen Prüfung und Zeigerbewegung kommt,
beschreibt jeder Eintrag eine Zeigerbewegung, die gemacht werden sollte,
und sein alter Wert ist der Wert, den der Zeiger wirklich hatte.
Eine Ablehnung, ein Konflikt oder ein fehlender Commit schreiben keinen Eintrag.
Der Preis ist, dass das Schreiben der kleinen Datei zum geschützten Abschnitt gehört.
Die Zeiger bewegt nur der Kern (\type{Repository}).
Er gibt die Referenzen und das Log zum Lesen heraus;
einen Eintrag bauen und schreiben kann nur Code des Kerns selbst.
Das ist eine Vereinbarung der Schnittstelle und keine Grenze,
denn die Dateien sind gewöhnliche Dateien.

Ein Eintrag bleibt trotzdem eine Absicht.
Das Dateisystem kann zwischen Eintrag und Zeigerbewegung ausfallen,
und ein Eintrag, der nicht als gesichert bekannt ist, verhindert die Zeigerbewegung.
Der Fehler sagt in beiden Fällen, dass ein Eintrag existiert
und dass sich der Zeiger nicht bewegt hat, und er trägt den Eintrag mit.
Ein Aufrufer kann so ein Scheitern ohne Eintrag von einem mit Eintrag unterscheiden
und weiss, ob er die Änderung wiederholen darf.
Ob eine Zeigerbewegung stattgefunden hat, lässt sich an der Kette der Einträge eines Zeigers
ablesen.
Nach der Zeigerbewegung wird nichts mehr geschrieben, damit nichts halb geschrieben bleiben kann.

Was nach einem Absturz an jeder Stelle zurückbleibt, steht in
\in{Abbildung}[fig:oplog-write] rechts.
Bis zum letzten Schritt bleibt dabei auch die Sperre liegen.
Der nächste Befehl auf demselben Rechner übernimmt sie;
bis dahin nennt das Log den Ausgang des neuesten Eintrags unbekannt.

\startinfobox
{\bf Was \quotation{gesichert} auf jeder Plattform heisst.}
Eine Datei ist erst nach einem Stromausfall noch da, wenn auch ihr Verzeichnis gesichert ist,
denn erst das Verzeichnis hält ihren Namen.
Unter Unix und unter Windows sichert der Kern deshalb das Verzeichnis,
nachdem er ein Objekt, einen Eintrag oder einen Zeiger an seinen Platz gelegt hat (ADR-007);
nur die Datei \type{oplog-tip} sichert er nach bestem Bemühen.
Kann ein Dateisystem ein Verzeichnis nicht sichern, meldet der Befehl einen Fehler.
Die Datei liegt dann an ihrem Platz, ist aber nicht als gesichert bekannt.
Ein Objekt oder ein Eintrag gilt deshalb als nicht geschrieben,
ein Zeiger dagegen als bewegt, wie oben beschrieben.
Auf anderen Plattformen bleibt jede Umbenennung atomar,
ein Stromausfall kann dort aber die letzte Änderung zurücknehmen.
\stopinfobox

\startinfobox
{\bf Wann das Log den Ausgang falsch einschätzt.}
Kehrt ein Zeiger innerhalb des Logs zu einem früheren Wert zurück,
entscheidet die Kette richtig, solange niemand den Zeiger ausserhalb des Logs bewegt,
denn jeder Eintrag liest seinen alten Wert unter der Sperre.
Setzt aber jemand ausserhalb des Logs einen Zeiger auf den alten Wert eines Eintrags zurück,
sieht das Log dasselbe wie nach einer gescheiterten Zeigerbewegung.
Es meldet dann, die Zeigerbewegung habe nicht stattgefunden, obwohl sie stattfand;
beim neuesten Eintrag eines Zeigers nur, solange niemand schreibt,
sonst ist der Ausgang unbekannt.
Umgekehrt sieht eine gescheiterte Zeigerbewegung,
nach der jemand den Zeiger ausserhalb des Logs auf den neuen Wert setzt,
wie eine Zeigerbewegung aus, die stattfand.
\stopinfobox

\subsection{Nummern und die Datei \type{oplog-tip}}

Jeder Eintrag entsteht in einer temporären Datei in \type{tmp/}
und wird dann mit einem harten Verweis unter der nächsten freien Nummer veröffentlicht.
Der Verweis scheitert, wenn die Nummer vergeben ist,
und ein Eintrag ist vom ersten Moment an vollständig.
Schreiber, die die Sperre halten, treffen hier nicht aufeinander;
die Wiederholung mit der nächsten Nummer gilt für Schreiber ohne Sperre.
Eine Lücke in den Nummern meldet der Leser als verlorenen Eintrag.

Was in \type{tmp/} liegen bleibt, räumt der nächste Schreiber auf, sobald er die Sperre nimmt.
Jeder, der in \type{tmp/} schreibt, hält die Sperre der Referenzen:
die Befehle, die schreiben, die Zeigerbewegungen und der Purge.
Wer die Sperre nimmt, ist also der einzige Schreiber,
und jede Datei in \type{tmp/} stammt aus einem Schreiben, das scheiterte oder abgebrochen wurde.
Gleich nach dem Nehmen entfernt er darum jede Datei in \type{tmp/}, ohne einem Verweis zu folgen,
und jedes Verzeichnis neben \type{.stemma}, das ein abgebrochenes \type{init} zurückliess.
Es zählt allein die Sperre; das Alter einer Datei spielt keine Rolle.
So wird ein langsamer Schreiber wie das erste \type{track} vieler Dateien nie unterbrochen,
und es gibt keinen Befehl, an den man denken müsste.

\startinfobox
{\bf Grenzfälle beim Aufräumen.}
\startitemize
\item Ein Verzeichnis eines abgebrochenen \type{init} erkennt der Schreiber an seinem ganzen
Namen: \type{.stemma-init-}, die Prozessnummer, ein Zähler und 16 kleine Hexadezimalziffern.
Ein Verzeichnis des Projekts wie \type{.stemma-init-notes} gehört zum Inhalt und bleibt.
\item Besteht das Journal eines Purge, räumt ein abgewiesener Befehl nichts auf;
das übernehmen \type{purge --resume} und \type{--abort}.
\item Das Aufräumen geschieht nach bestem Bemühen:
Was sich nicht entfernen lässt, bleibt, und der nächste Schreiber versucht es wieder.
\stopitemize
\stopinfobox

\startinfobox
{\bf Grenzfälle beim Schreiben eines Eintrags.}
\startitemize
\item Ein Eintrag hat eine Obergrenze von 64 KiB.
Der Schreiber lehnt einen grösseren Eintrag ab, bevor er etwas schreibt.
Der Leser lehnt eine grössere Datei ohnehin ab,
und ohne die Grenze beim Schreiber würde ein sehr langer Akteur ein Log erzeugen,
das sich schon ab dem ersten Eintrag nicht mehr lesen lässt.
\item Die temporäre Datei entfernt der Schreiber nach bestem Bemühen.
Bleibt sie liegen, ist der Eintrag trotzdem vollständig, und die Zeigerbewegung geht weiter,
denn ein Aufräumen darf keine Zeigerbewegung verhindern.
\item Der Leser meldet eine Lücke erst, nachdem er das Verzeichnis ein zweites Mal gelesen hat,
denn während eines Schreibens liefert das Auflisten eines Verzeichnisses keinen festen Stand.
Namen mit einem Punkt am Anfang überspringt er, jeden anderen fremden Namen meldet er.
\stopitemize
\stopinfobox

Die Datei \type{oplog-tip} hält die Nummer des letzten Eintrags.
Der Schreiber führt sie nach dem Eintrag nach, noch bevor sich ein Zeiger bewegt.
Fehlt dem Verzeichnis der letzte Eintrag, nennt die Datei eine grössere Nummer, als es hat.
Dann meldet der Leser den Verlust, und der Schreiber schreibt nichts,
denn sonst würde er die Nummer ein zweites Mal an eine andere Zeigerbewegung vergeben.
Eine Datei, die um eins zurückliegt, ist kein Fehler:
Der Vorgang brach zwischen dem Eintrag und der Datei ab,
und der nächste Schreiber führt sie nach.
Gegen einen Angriff hilft die Datei nicht, nur gegen Unfälle.
Wer sie löscht, fällt erst \type{stemma op verify} auf,
sofern der letzte Eintrag in der Kette steht,
und wer den Eintrag und die Datei neu schreibt, bleibt unbemerkt.

\startinfobox
{\bf Grenzfälle der Datei \type{oplog-tip}.}
\startitemize
\item Die Datei selbst wird gesichert, ihr Verzeichnis nur nach bestem Bemühen.
\item Leser und Schreiber lesen die Datei, bevor sie das Verzeichnis auflisten.
Ein Schreiber legt den Eintrag an, bevor er die Datei nachführt.
In der anderen Reihenfolge würde ein Leser, der gerade mit einem Schreiber zusammentrifft,
einen Verlust melden, den es nicht gibt.
\item Liess sich die Datei nicht schreiben, liegt sie um eins zurück,
und der nächste Schreiber führt sie nach.
\item Nach einem Eintrag, dessen Verzeichnis sich nicht sichern liess, rückt die Datei nicht vor,
sonst würde sie nach einem Absturz jeden weiteren Schreiber abweisen.
\item Fehlt die Datei (ein Repository vor ihrer Einführung), legt der nächste Eintrag sie an.
\item Eine Lücke in der Mitte hält den Schreiber nicht auf,
denn eine Weigerung würde die Zeigerbewegung verhindern, die das Log reparieren soll.
\stopitemize
\stopinfobox

\subsection{Die Hash-Kette}

Ein Log aus Textdateien lässt sich leicht ändern.
Die Hash-Kette macht eine Änderung sichtbar:
Jeder Eintrag nennt in der Zeile \type{previous} den Hash des Eintrags davor,
und der erste Eintrag der Kette hat \type{previous -}.
Der Hash ist ein BLAKE3 über einen Umschlag:
die Nummer, die Zeit, den Akteur, den Hash des Vorgängers und den Hash des Rumpfs.
Der Rumpf sind die Zeilen nach \type{previous}, also die Operation und die Zeiger.
\in{Abbildung}[fig:oplog-chain] zeigt vier Einträge,
von denen ein Purge einen durch einen Stub ersetzt hat.

\startplacefigure[title={Hash-Kette mit Stub, \type{oplog-tip} und Anker},
    reference=fig:oplog-chain,location=here]
\externalfigure[images/oplog-chain.pdf][width=\textwidth]
\stopplacefigure

Der Leser prüft die Kette.
Wird ein Eintrag in der Mitte geändert, gelöscht, eingefügt oder mit einem anderen vertauscht,
bricht sie an dieser Stelle, und der Leser nennt die Nummer.
Auf den letzten Eintrag verweist noch keiner,
deshalb nennt die Datei \type{oplog-tip} neben der Nummer auch seinen Hash.
So fällt auch ein ersetzter letzter Eintrag auf,
und der Schreiber hängt keinen neuen Eintrag an einen ersetzten an.
Ein Stub behält den Hash des Rumpfs, den er ersetzt, und damit den Hash des Eintrags;
die Kette hält über einen Purge hinweg (ADR-014).

Der Schreiber liest den Eintrag vor der Nummer, die er versucht, und nennt dessen Hash.
Verliert er das Rennen um eine Nummer, baut er seinen Eintrag für die nächste Nummer neu,
mit dem Hash ihres Vorgängers.
Kann er den Vorgänger nicht lesen, schreibt er nichts,
denn ein Neubeginn der Kette würde den Schaden verdecken.
Aus demselben Grund schreibt er nichts hinter einen alten Eintrag,
der auf einen Eintrag der Kette folgt.

\type{op log} prüft mit einer Grenze nur das gezeigte Fenster
und dessen Anschluss an den Eintrag davor;
lässt sich dieser nicht lesen, warnt der Befehl.
\type{stemma op verify} prüft das ganze Log und gibt einen Anker aus,
die Nummer und den Hash des letzten Eintrags, sofern dieser in der Kette steht.
Die Datei \type{oplog-tip} prüft er strenger als die übrigen Befehle:
Fehlt sie oder liegt sie mehr als einen Eintrag zurück,
obwohl der letzte Eintrag in der Kette steht, meldet er das,
denn dann haben die Schreiber nichts mit ihr verglichen.

Die Kette zeigt, dass die Einträge zueinander passen, nicht wer sie schrieb.
Wer \type{.stemma} schreiben kann, kann jeden späteren Hash und die Datei \type{oplog-tip}
neu berechnen.
Das fällt nur mit einem Anker auf, der ausserhalb des Repositories liegt:
Wer einen Anker aufbewahrt, prüft ihn später mit \type{stemma op verify --anchor}.
Für die Arbeit mit Agenten zählt das besonders:
Ein Agent, der im Repository arbeitet, kann \type{.stemma} schreiben,
und erst ein Anker beim Sponsor zeigt, ob das Log nach der Sitzung noch dasselbe ist.
Signaturen der Akteure (ADR-004) und ein Hub, der den letzten Eintrag bestätigt (Phase 5),
wären Anker, die der Akteur selbst nicht ändern kann; beide sind offen.

\startinfobox
{\bf Logs aus der Zeit vor der Kette.}
Ein solches Log behält seine alten Einträge vorne, und der erste neue Eintrag beginnt die Kette.
Diese alten Einträge deckt die Kette nicht ab,
und einen alten Eintrag hinter der Kette lehnt der Leser ab.
\stopinfobox

\subsection{Den Zustand vor einem Eintrag wiederherstellen}

Jeder Eintrag trägt den alten und den neuen Wert seiner Zeiger,
also lässt sich eine Operation zurücksetzen, indem die alten Werte zurückkommen
(ADR-011, ADR-013).
Die Zeiger allein reichen dafür nicht.
Setzt das Restore nur sie zurück, liest der nächste Snapshot das unveränderte Verzeichnis
und stellt den neuen Stand wieder her,
denn der Working-Copy-Commit ist der Zustand des Verzeichnisses (ADR-010).
Das Restore schreibt deshalb auch die Dateien des alten Baums ins Verzeichnis.

Für die Arbeit mit Agenten ist das Restore der Rückweg.
Ein Agent führt viele Schritte aus, ohne dass ein Mensch jeden prüft.
Geht einer schief, setzt ein Mensch oder der Agent selbst Zeiger und Verzeichnis
auf den Stand davor zurück.
Weil das Restore ein eigener Eintrag ist, bleibt auch der verworfene Stand im Log,
und \type{--dry-run} zeigt den Plan, bevor etwas geschieht.

In der Sitzung nimmt \type{op restore 5} den zweiten Commit zurück.
Mit \type{--dry-run} zeigt der Befehl vorher, welche Zeiger er setzt
und welche Dateien er schreibt oder entfernt, und schreibt nichts.
Hier sind die beiden Bäume gleich, also nennt der Plan nur Zeiger:

\starttyping
$ stemma op restore --dry-run 5
Would restore the state before entry 5; nothing is written
    working-copy  b3:e394…b6eb -> b3:7694…d054
    branch main  b3:9d8a…4c77 -> b3:2037…df79
$ stemma op restore 5
Restored the state before entry 5 as entry 6
To undo it: stemma op restore 6
$ cat README.md
Hallo Welt
$ stemma status
Working copy changes:
M README.md
\stoptyping

Der Branch \type{main} steht wieder auf dem Commit \quotation{Erste Fassung}.
Die Änderung an \type{README.md} bleibt,
denn vor Eintrag 5 hatte der Working-Copy-Commit sie schon:
Der Snapshot von \type{status} hat sie in Eintrag 4 gespeichert.
Das Restore nimmt also den Commit zurück und lässt die Änderung im Working-Copy-Commit.
Wer auch sie zurücknehmen will, stellt danach den Zustand vor Eintrag 4 her.

Das Restore läuft in diesen Schritten ab:

\startitemize[n]
\item Der Kern prüft, ob der Akteur das Restore machen darf (\type{authorize}),
und beurteilt den Eintrag.
Dann plant er:
Jeder Commit, auf den ein Zeiger zurück soll, muss im Speicher liegen,
und keine unverfolgte Datei darf dort stehen, wo eine Datei des alten Baums hin soll.
Bis hier ist nichts geschrieben.
\item Er nimmt die Sperre der Referenzen.
Sie kommt erst nach der Beurteilung,
denn eine gehaltene Sperre lässt den neuesten Eintrag unfertig aussehen.
\item Er macht einen Snapshot, damit keine ungesicherte Änderung verloren geht,
und plant unter der Sperre neu, vom Baum des Snapshots aus.
\item Er schreibt den Eintrag \type{restore}.
\item Er schreibt die Dateien des alten Baums ins Verzeichnis.
\item Er bewegt die Branches auf ihre Werte vor dem Eintrag.
\item Er bewegt den Working-Copy-Commit und zuletzt HEAD.
\item Er gibt die Sperre frei.
\stopitemize

\in{Abbildung}[fig:restore-flow] zeigt den Ablauf mit den Stellen,
an denen ein Absturz etwas zurücklässt.

\startplacefigure[title={Ablauf eines Restore mit Absturzpunkten},
    reference=fig:restore-flow,location=here]
\externalfigure[images/restore-flow.pdf][width=0.9\textwidth]
\stopplacefigure

Das Restore setzt jeden Zeiger für sich zurück.
Es setzt jeden Zeiger, den der Eintrag nennt, auf seinen alten Wert,
und ein Zeiger, der schon dort steht, bleibt, wie er ist.
So lässt sich auch ein Eintrag zurücksetzen, der nur zur Hälfte stattgefunden hat,
und ein abgebrochenes Restore beendet derselbe Aufruf:
Was schon stimmt, bleibt, und der Rest folgt.
Ein Restore ist eine Operation mit eigenem Eintrag und schreibt das Log nie um;
nur ein Purge ersetzt Einträge durch Stubs.
Ein Restore lässt sich deshalb selbst wieder zurücksetzen,
in der Sitzung mit \type{op restore 6}.

\startinfobox
{\bf Wie das Restore das Verzeichnis schreibt.}
\startitemize
\item Das Schreiben übernimmt eine eigene Schicht,
die auch der spätere Checkout von Branches braucht (\type{checkout.rs}).
Sie plant zuerst und schreibt danach.
\item Sie fasst nur Pfade an, die der alte oder der neue Baum nennt.
Unverfolgte Dateien, \type{.stemma} und \type{.git} lässt sie in Ruhe.
\item Ein verfolgter Pfad wird auch dann zurückgesetzt,
wenn die Ausschlussdatei ihn heute ausschliesst (ADR-012).
\item Sie schreibt nie durch einen Link, lehnt Namen ab, die Windows nicht halten kann,
und erkennt Namen,
die auf einem Dateisystem ohne Unterscheidung der Gross- und Kleinschreibung zusammenfallen.
\item Jede Datei geht über eine temporäre Datei und ein \type{rename},
damit ein Leser die alte oder die neue Fassung sieht.
Ist seit der Planung eine Datei im Weg aufgetaucht, bricht sie ab.
\stopitemize
\stopinfobox

\startinfobox
{\bf Wann ein Restore ablehnt oder \type{--force} braucht.}
\startitemize
\item Einen Stub und den Eintrag eines Purge lehnt es immer ab, auch mit \type{--force},
ebenso einen Eintrag, den ein unfertiger Purge nennt.
\item Einen Eintrag, der HEAD oder den Working-Copy-Commit erst angelegt hat,
wie den von \type{init}, lehnt es auch mit \type{--force} ab, denn beide können nicht fehlen.
Einen Branch, den ein Eintrag angelegt hat, entfernt es dagegen.
\item Ist der Ausgang des Eintrags unbekannt, braucht es \type{--force}.
Das gilt für jeden Eintrag vor dem jüngsten Stub,
für einen Eintrag, dessen Zeiger danach auf einem dritten Wert steht,
weil ihn jemand ausserhalb des Logs bewegt hat,
und für den Eintrag, der einen Zeiger zuletzt bewegt hat,
solange \type{refs.lock} liegt und der Zeiger nicht auf dem neuen Wert steht.
Im letzten Fall klärt auch ein anderer Befehl, der schreibt, den Ausgang,
denn er übernimmt die Sperre.
\item Muss kein Zeiger zurück, schreibt das Restore nichts, auch keinen Eintrag.
\item \type{--dry-run} schreibt nichts, nicht einmal den Snapshot.
Eine ungesicherte Änderung im Verzeichnis sieht der Plan deshalb nicht.
\stopitemize
\stopinfobox

\subsection{Ein Geheimnis aus Verlauf und Log entfernen}

Gerät ein Schlüssel in eine verfolgte Datei, hält ihn der nächste Snapshot fest,
und das Log behält jeden Commit, den eine Operation verlassen hat.
Ein Restore hilft dagegen nicht, denn es entfernt nichts.
Ein Purge entfernt den Schlüssel wieder (ADR-014).
Er nimmt die ID des Blobs, der den Schlüssel enthält,
schreibt jeden Commit um, der ihn erreicht, und löscht die alten Objekte.
Ein Commit, dessen Baum den Blob enthält, bekommt einen Baum ohne ihn,
und jeder Commit danach neue Eltern.
Die Einträge des Logs, die einen umgeschriebenen Commit nennen, werden zu Stubs.
Nur ein Mensch darf purgen, denn der Purge lässt sich nicht zurücksetzen.
Ein Agent, der einer eingeschleusten Anweisung folgt oder einen Fund falsch deutet,
könnte sonst Verlauf löschen, den kein Restore zurückbringt.
Er meldet das Geheimnis, und sein Sponsor entscheidet.

In der Sitzung gerät ein Zugangsschlüssel in den Verlauf.
Die ID des Blobs ist der BLAKE3-Hash über einen Kopf aus Art und Länge
und den Inhalt der Datei (\in{Abschnitt}[sec:object-ids], ADR-001, ADR-007);
einen Befehl, der sie zu einem Pfad nennt, gibt es noch nicht.
Bis dahin findet \type{grep -rl} den Inhalt im Objektspeicher,
denn ein loses Objekt liegt unkomprimiert unter \type{objects/b3/}.
Aus dem Pfad wird die ID, indem man \type{b3:} voranstellt und den Schrägstrich weglässt.
Ohne \type{--apply} zeigt \type{purge} nur den Plan und schreibt nichts:

\starttyping
$ echo "token=7f3a9c" > .env
$ stemma track .env
tracked .env
$ stemma commit -m "Zugang"
Committed b3:930a…db53 on main
$ grep -rl 'token=7f3a9c' .stemma/objects
.stemma/objects/b3/4c/bc3d…156b
$ stemma purge b3:4cbc…156b
Would purge blob b3:4cbc…156b; nothing is written
    rewrite b3:930a…db53 -> b3:dd97…5918
    rewrite b3:f082…a60c -> b3:35cb…f216
    rewrite b3:fece…6cbb -> b3:1085…c853
    working-copy  b3:f082…a60c -> b3:35cb…f216
    branch main  b3:930a…db53 -> b3:dd97…5918
    stub entries 7-8
    delete commit b3:930a…db53
    delete commit b3:f082…a60c
    delete commit b3:fece…6cbb
    delete tree b3:4094…7ab2
    delete blob b3:4cbc…156b
Run it with --apply; a purge cannot be undone
\stoptyping

Umgeschrieben werden der Commit \quotation{Zugang}, der Working-Copy-Commit danach
und die Fassung des Working-Copy-Commits, die \type{track} gespeichert hat.
Change-ID, Autor, Zeit und Nachricht behält jeder,
damit sich eine Änderung über den Purge hinweg verfolgen lässt.
Ein Verzeichnis, das nur den Blob enthielt, fällt aus dem Baum,
so wie ein Snapshot nie ein leeres Verzeichnis anlegt.
Gelöscht wird, was das Umschreiben ersetzt hat,
und dazu Reste im Objektspeicher, die den Blob enthalten oder auf einen Commit mit ihm folgen;
nach solchen Resten, die nichts erreicht, durchsucht der Plan den ganzen Speicher.
Zum Schluss prüft er, dass nichts Behaltenes den Blob noch enthält
oder etwas erreicht, das er löscht; sonst bricht er ab.
\in{Abbildung}[fig:purge-graph] zeigt den Verlauf und das Log vor und nach dem Purge.

\startplacefigure[title={Verlauf und Log vor und nach einem Purge},
    reference=fig:purge-graph,location=here]
\externalfigure[images/purge-graph.pdf][width=\textwidth]
\stopplacefigure

Mit \type{--apply} wird der Purge gemacht.
Die erste Zeile nennt den Eintrag des Purge, darunter stehen dieselben Zeilen wie im Plan.
Zuletzt nennt der Purge die Pfade, an denen der Verlauf den Blob hielt,
und rät, sie in \type{.stemmaignore} aufzunehmen.
Danach zeigt \type{op log} den Eintrag \type{purge} und die beiden Stubs,
und die Datei mit dem Schlüssel ist nicht mehr verfolgt:

\starttyping
$ stemma purge b3:4cbc…156b --apply
Purged blob b3:4cbc…156b as entry 9 of the operation log
    ...
    delete blob b3:4cbc…156b
The secret was at these paths; a file that is still there is untracked now,
but `track .` saves it again, so name it in `.stemmaignore` or remove it:
    path .env
$ stemma op log
9  2026-10-24T05:54:35Z  human daniel  purge
    commits 3  stubs 7-8
8  2026-10-24T05:54:33Z  human daniel  (purged)
7  2026-10-24T05:54:31Z  human daniel  (purged)
6  2026-10-24T05:54:28Z  human daniel  restore
    working-copy  b3:e394…b6eb -> b3:7694…d054
    branch main  b3:9d8a…4c77 -> b3:2037…df79
    ? it is not known whether the move took effect
...
$ stemma status
Untracked files:
? .env
$ stemma op restore 8
stemma: entry 8 was replaced by a stub when a secret was purged,
so what it moved is gone and it cannot be restored
\stoptyping

Ein Stub behält Nummer, Zeit und Akteur und verliert die Operation und jede ID.
Der Eintrag des Purge nennt keinen Zeiger und keine ID,
nur die Zahl der umgeschriebenen Commits und die Nummern der Stubs als Bereiche;
eine lange Liste verteilt sich auf mehrere Einträge.
Weil ein Stub Zeigerbewegungen ersetzt, die niemand mehr kennt,
ist der Ausgang jedes Eintrags vor dem jüngsten Stub unbekannt.
Deshalb tragen die Einträge 1 bis 6 nun die Zeile mit dem Fragezeichen,
und ein Restore eines solchen Eintrags braucht \type{--force}:

\starttyping
$ stemma op restore 3
stemma: the log does not show whether entry 3 took effect, so the state
before it may not be what it says; use --force to restore anyway
\stoptyping

Die Datei \type{.env} bleibt im Verzeichnis;
ein späteres \type{track .} nimmt sie wieder auf,
sofern \type{.stemmaignore} sie nicht ausschliesst. Deshalb nennt der Purge ihren Pfad.
In der Sitzung schliesst eine Zeile die Datei aus:

\starttyping
$ echo ".env" > .stemmaignore
$ stemma status
Untracked files:
? .stemmaignore
\stoptyping

Nach dem Purge prüft \type{op verify} das ganze Log und gibt den Anker aus.
Wer den Anker ausserhalb des Repositories aufbewahrt, prüft später mit \type{--anchor},
ob der Eintrag noch denselben Hash hat:

\starttyping
$ stemma op verify
Checked 9 entries of the operation log: the hash chain holds.
anchor 9:b3:29a9…9450
$ stemma op verify --anchor 9:b3:29a9…9450
Checked 9 entries of the operation log: the hash chain holds.
Entry 9 still has the hash of the anchor.
anchor 9:b3:29a9…9450
\stoptyping

In der Ausgabe stehen die umbrochenen Meldungen auf einer Zeile.
Eine dauerhafte Liste der entfernten Blobs, die \type{track} prüft, folgt später (ADR-014).
Ein mit \type{--resume} beendeter Purge nennt keine Pfade, denn das Journal hält sie nicht fest.

\startinfobox
{\bf Stubs im Log.}
\startitemize
\item Ein Stub behält den Hash des Rumpfs, den er ersetzt (\type{stub b3:…}).
Damit behält er den Hash des ganzen Eintrags,
und die Kette hält über einen Purge hinweg, während Zeit und Akteur weiter geschützt sind
(\in{Abbildung}[fig:oplog-chain], ADR-014).
\item In der Hash-Kette haben Stub und Eintrag \type{purge}
die Version 3 der Kodierung wie jeder andere Eintrag;
ein Stub eines Eintrags aus der Zeit vor der Kette behält die Version 2.
\item Ein Stub, den kein Purge nennt, ist ein Fehler des Logs wie eine Lücke.
\stopitemize
\stopinfobox

Ein Purge läuft über ein Journal, damit ein Abbruch ihn nicht halb gemacht zurücklässt.
\in{Abbildung}[fig:purge-states] zeigt die Schritte mit \type{--apply};
die Abbildung teilt Schritt 6 am Punkt ohne Rückkehr in 6a und 6b.

\startitemize[n]
\item Der Purge lehnt einen Agenten ab, bevor er etwas schreibt.
\item Er speichert das Verzeichnis in einem Snapshot,
damit eine Änderung mit dem Geheimnis in einem Commit und im Plan steht.
\item Er nimmt die Sperre der Referenzen, hält sie bis zum Ende und plant unter ihr neu.
Sein Plan kann daher vom gezeigten abweichen.
\item Er hebt das Repository auf das Format 4, falls es noch tiefer steht,
und schreibt das Journal \type{.stemma/purge-pending}.
Es nennt den Blob, die Nummer des letzten Eintrags, jeden umgeschriebenen Commit,
die Bewegungen der Zeiger, die Stubs, die neuen Objekte und die Objekte, die gelöscht werden.
\item Er schreibt die neuen Bäume und Commits.
\item Er prüft, dass jeder Zeiger noch auf seinem alten Wert steht,
schreibt den Eintrag \type{purge} und bewegt die Zeiger.
\item Er ersetzt die Einträge durch Stubs.
\item Er löscht die alten Commits, die alten Bäume und den Blob
und entfernt zuletzt das Journal.
\stopitemize

Das Format kommt vor dem Journal,
denn ein Programm, das nur das Format 2 kennt, kennt auch das Journal nicht
und würde an ihm vorbei schreiben; so lehnt ein solches Programm das Repository ab.
Solange das Journal besteht, lehnt jeder andere Befehl, der schreibt, ab,
wenn er die Sperre nimmt.
Die Meldung nennt \type{stemma purge --resume} und \type{--abort}.

\startplacefigure[title={Zustände eines Purge mit \type{--resume} und \type{--abort}},
    reference=fig:purge-states,location=here]
\externalfigure[images/purge-states.pdf][width=0.9\textwidth]
\stopplacefigure

Der Eintrag \type{purge} ist der Punkt ohne Rückkehr.
Solange er fehlt, ist nichts verloren:
\type{stemma purge --abort} entfernt die neuen Objekte und das Journal,
und ein Objekt, das der Speicher schon vorher hatte, bleibt.
Das Format bleibt dabei 4, denn eine Version sinkt nie.
Ist der Eintrag geschrieben, geht der Purge nur noch vorwärts, und \type{--abort} lehnt ab.
\type{stemma purge --resume} beendet den Purge aus dem Journal.
Jeder Schritt lässt sich wiederholen:
Ein Objekt, das schon da ist, bleibt, ein Zeiger auf seinem neuen Wert wird übersprungen,
ein geschriebener Eintrag \type{purge} wird gefunden und nicht noch einmal geschrieben,
ein Stub ersetzt sich selbst, und ein gelöschtes Objekt ist weg.
Ein Zeiger, der auf keinem der beiden Werte steht, hält das Fortsetzen an,
und die Meldung nennt ihn.

\startinfobox
{\bf Die Sperre beim Fortsetzen.}
\startitemize
\item Eine Sperre, die der Abbruch zurückliess, nimmt \type{--resume} als die des Purge
und ersetzt sie,
ausser ein laufender Prozess hält sie noch oder sie nennt einen anderen Rechner.
\item Einen Purge ohne Sperre des Betriebssystems, etwa einer älteren Version,
erkennt es nicht.
\item Kann \type{--resume} selbst keine Sperre des Betriebssystems nehmen,
ersetzt es nur eine Datei in der alten Form, wie sie ein solcher Purge zurücklässt.
\stopitemize
\stopinfobox

Jeder Befehl, der schreibt, nimmt die Sperre der Referenzen,
bevor er sein erstes Objekt schreibt, und hält sie bis zu seiner letzten Zeigerbewegung.
Sonst findet ein Befehl, der vor dem Journal geprüft hat
und seinen Zeiger erst nach dem Purge bewegt, kein Journal mehr.
Er kann dann einen Commit nennen, dessen Blob der Purge inzwischen gelöscht hat,
obwohl der Befehl ihn noch einmal gespeichert hat.
Hält er die Sperre schon beim Speichern, kann kein Purge beginnen, und umgekehrt.
Ein Zähler der Purges oder eine Prüfung aller Objekte unter der Sperre
hätten das ebenfalls verhindert; die Sperre ist die einfachste Regel (ADR-014).
Sie wird dafür so lange gehalten, wie der Snapshot dauert,
bei 10'000 Dateien etwa 0,7 Sekunden
(Release-Build, macOS mit APFS auf einer SSD, ein Lauf, Dateien zu 1 KiB; ADR-010).

Ctrl-C entfernt die Sperre, bevor der Prozess endet.
Nach \type{kill -9} oder einem Absturz bleibt die Datei \type{refs.lock} liegen,
und der nächste Befehl, der schreibt, übernimmt sie;
nach einem abgebrochenen Purge tun das nur \type{--resume} und \type{--abort}.
Wer die Sperre hält, hält dazu eine Sperre des Betriebssystems
auf der Datei \type{refs.lock.guard} (ADR-008),
und die gibt das Betriebssystem frei, wenn der Prozess endet, wie auch immer er endet.
Ist diese Sperre frei und nennt \type{refs.lock} in der Form, die ihr Halter schreibt,
diesen Rechner, war der Halter ein beendeter Prozess.
Die Regel braucht keine Frist und fragt das Betriebssystem nicht nach einer Prozessnummer.

\startinfobox
{\bf Grenzfälle beim Übernehmen der Sperre.}
\startitemize
\item Nennt die Datei die Nummer des eigenen Prozesses, übernimmt der Befehl sie trotzdem:
Ein früherer Prozess hatte sie,
etwa in einem Container, in dem der Befehl stets als derselbe Prozess läuft.
\item Eine Datei eines anderen Rechners übernimmt kein Befehl,
denn teilen sich zwei Rechner ein Dateisystem,
reicht die Sperre des Betriebssystems nicht immer von einem zum anderen.
Die Meldung nennt dann den Rechner und den Prozess.
\item Die Regel setzt voraus, dass keine zwei Rechner, die ein Repository teilen, gleich heissen.
Namen wie \type{localhost} gelten deshalb als unbekannt.
\item Kann ein Befehl die Sperre des Betriebssystems nicht nehmen,
etwa auf einem Dateisystem ohne Dateisperren,
schreibt er die Datei in der alten Form und übernimmt keine Sperre;
die Meldung nennt den Grund.
\stopitemize
\stopinfobox

\subsection{Wie lange das Log Einträge behält}

Ein Snapshot bei jedem Befehl schreibt viele Einträge, und jeder nennt den Working-Copy-Commit,
den er ersetzt hat. In Phase~1 behält das Log trotzdem jeden Eintrag und der Speicher jedes
Objekt (ADR-011). Eine echte Sitzung eines Agenten gibt es noch nicht, deshalb hat
\type{scripts/measure-retention.sh} eine nachgespielt: die 110 Commits im Verlauf dieses
Repositories bis \type{11f06a4}, vom 18. bis zum 23.~Oktober 2026, also sechs Tage. In der
feinen Variante wird jede geänderte Datei einzeln geschrieben, und danach folgt ein Befehl, wie
bei einem Agenten, der nach jeder Änderung einen Befehl aufruft. Die grobe Variante ruft
\type{track .} einmal je Commit auf. Keine der beiden ruft \type{commit} auf. Gemessen wurde
einmal je Variante, mit dem Release-Build unter macOS~27 mit APFS auf einer SSD; die Grössen

aus. Den Platz brauchen die Fassungen weniger grosser Dateien, nicht die Zahl der Snapshots:
Ein Snapshot je Befehl hält nur etwa 6 Prozent mehr am Leben als einer je Commit. Solange es
keine Garbage Collection gibt (ADR-007), gibt das Entfernen eines Eintrags ohnehin kein Byte
frei, denn seine Objekte bleiben im Speicher. Werden die Daten zu gross, helfen zuerst
Pack-Dateien mit Deltas, die keinen Zustand verlieren.

Für später steht fest, wie Aufbewahrung und Garbage Collection zusammenspielen. Die Garbage
Collection behält jedes Objekt, das eine Referenz oder der alte oder neue Wert eines Eintrags
erreicht, der kein Stub ist; die Regel steht vollständig in ADR-011. Eine Aufbewahrungsregel
ersetzt Einträge \type{snapshot} durch denselben Stub wie der Purge;
sie löscht keinen Eintrag und legt keine zusammen. So bleiben die Nummern lückenlos und die
Hash-Kette ganz, und es braucht keinen Punkt, an dem die Kette neu beginnt. Einträge anderer
Operationen bleiben, und mindestens der jüngste Snapshot bleibt.

Der Preis ist höher als beim Purge. Ein Stub ist eine Grenze für den Ausgang: Jeder ältere
Eintrag gilt danach als unbekannt, auch ein \type{commit}, ein \type{track} oder ein
\type{restore}, und sein Restore braucht \type{--force}. Ein Purge ist selten, eine
Aufbewahrungsregel läuft immer wieder. Aufbewahrung und Garbage Collection kommen in einem
Schritt, denn das eine nützt ohne das andere nichts.

\section{Wie die strengen Leser geprüft werden}

Jeder Leser einer Datei des Repositories ist streng: Er nimmt nur an, was der Schreiber
geschrieben hätte (ADR-005). Das gilt für Bäume, Commits, die Zeile des Akteurs, den Index,
die Einträge des Operation Log in beiden Kodierungen und das Journal eines Purge. Daraus folgt
eine Regel, die sich an jeder beliebigen Eingabe prüfen lässt: Entweder lehnt der Leser sie ab,
oder das Kodieren dessen, was er gelesen hat, ergibt genau die Eingabe. Eine Ablehnung hat eine
Meldung, und ihre Kette von Ursachen endet; nur der Leser des Journals meldet bloss, dass es
beschädigt ist.
Eine zweite Schreibweise derselben Sache gibt es dann nicht, und damit auch keine zweite ID.

Mehrere Arten von Tests prüfen diese Regel. Die Golden Vectors legen die Bytes einzelner Objekte
fest und ändern sie an je einer Stelle. Die Property-Tests in \type{properties.rs} erzeugen
Tausende Eingaben: gültige Kodierungen, die an mehreren Stellen zugleich verändert sind,
zusammengeklebte Stücke zweier Kodierungen, Bruchstücke des Formats und rohe Bytes. Der
Startwert des Generators ist fest, damit ein Fehler wiederholbar ist; mit
\type{STEMMA_PROPERTY_SEED} und \type{STEMMA_PROPERTY_CASES} lassen sich andere und mehr
Eingaben prüfen. Golden Vectors und Property-Tests laufen in \type{just ci}.

Der Generator sieht aber nicht, welche Zweige eines Lesers er erreicht. Das tut ein Fuzzer,
der der Abdeckung folgt: \type{cargo fuzz} mit libFuzzer verändert die Eingaben so, dass sie
neue Zweige erreichen. Im Verzeichnis \type{fuzz/} gibt es dafür sechs Ziele, eines je Leser:
\type{tree}, \type{commit}, \type{actor}, \type{index}, \type{entry} und \type{journal}.
Die Leser von HEAD und einer Branch-Datei lesen nur eine Zeile; für sie genügen die
Property-Tests. Die Ziele beginnen bei gültigen Kodierungen in \type{fuzz/seeds/}.
libFuzzer braucht die Nightly-Version von Rust, deshalb gehört das Fuzzing nicht zu
\type{just ci}. Es läuft von Hand:

\starttyping
rustup toolchain install nightly
cargo install cargo-fuzz --locked
just fuzz entry 300      # ein Leser, 300 Sekunden
just fuzz-all 60         # alle Leser, je 60 Sekunden
\stoptyping

Ein Fund liegt danach in \type{fuzz/artifacts/ZIEL/} und lässt sich mit
\type{cargo +nightly fuzz run ZIEL DATEI} wiederholen. \type{just fuzz-all} lässt jedes Ziel
laufen und scheitert am Ende, wenn eines etwas gefunden hat. Der von Hand gestartete Workflow
der CI hat einen Job, der jedes Ziel eine Minute lang laufen lässt und die Funde aufbewahrt.

Schon der Property-Test des Journals hat einen Fehler gefunden. Die Zeile
\type{stubs 1-999999999999} ist nur wenige Bytes lang, doch der Leser schrieb jede Nummer des
Bereichs einzeln in eine Liste, und das Programm lief aus dem Speicher, statt das Journal als
beschädigt zu melden. Der Leser prüft die Bereiche jetzt, bevor er sie ausschreibt: Ein Stub
nach dem letzten Eintrag, den das Journal nennt, und mehr als $2^{24}$ Stubs sind Schaden.
Damit kein Purge ein Journal schreibt, das er selbst nicht wieder lesen kann, lehnt schon der
Plan einen Purge ab, der mehr als $2^{24}$ Einträge ersetzen würde.

Für Code, den Agenten schreiben, sind Property-Tests und Fuzzer eine Prüfung,
die nicht vom Urteil des Agenten oder der Person im Review abhängt:
Sie prüfen eine Regel an Eingaben, an die niemand gedacht hat.
Der Fehler im Leser des Journals ist so gefunden worden.

\section{Offene Fragen}

Die Fragen, die Phase~1 zum Abschluss braucht, sind entschieden.
Vom Dateimodus speichert Stemma nur das Ausführbit, weitere Rechte und Metadaten nicht
(ADR-010). Ein symbolischer Link wird als sein Ziel gespeichert,
und ein Ziel, das kein UTF-8 ist, lehnt der Snapshot ab (ADR-010).
Einen Index als Datei gibt es nicht, denn die Arbeitskopie ist ein Commit (ADR-010);
das Textformat \type{stemma-index 1} gilt nur, falls der Index später als Cache gespeichert
wird (ADR-005).

Offen für spätere Phasen bleiben diese Punkte:

\startitemize
\item Aufbewahrung und Garbage Collection kommen in einem Schritt,
gemessen an einer echten Sitzung eines Agenten (ADR-007, ADR-011);
bis dahin wächst der Speicher nur.
\item Die Prüfung des Besitzers von \type{.stemma} ist nicht frei von Wettläufen,
unter Windows lehnt sie nur ein \type{.stemma} im Wurzelverzeichnis eines Laufwerks ab,
und \type{init} ersetzt unter Unix ein leeres \type{.stemma},
das ein anderer Prozess im falschen Augenblick anlegt (ADR-009).
\item Die Regel, dass jeder Akteur in einer eigenen Arbeitskopie arbeitet,
setzt der Kern noch nicht durch; das kommt mit der zweiten Arbeitskopie in Phase~3 (ADR-010).
\item Ein Repository ohne die Datei \type{working-copy} lässt sich nicht mehr reparieren,
eine verfolgte Spezialdatei hält jeden Snapshot an,
und ein verfolgtes Verzeichnis, das zum Link wird, verliert seine Dateien ohne Warnung.
Die Dateien eines Snapshots stammen nicht aus einem einzigen Augenblick (ADR-010).
\item Kein Befehl repariert eine gebrochene Hash-Kette oder ein Log ohne seinen letzten Eintrag,
und einen Anker, den der Akteur nicht ändern kann, liefern erst Signaturen oder der Hub
(ADR-011).
\item Muster der Ausschlussdatei vergleichen Bytes, auch auf einem Dateisystem,
das Gross- und Kleinschreibung oder Unicode-Formen gleichsetzt;
ob die Grenzen von 1024 Byte und 64 KiB passen, zeigen erst echte Dateien (ADR-012).
\item Der Plan eines Restore (\type{--dry-run}) macht keinen Snapshot
und sieht ungesicherte Änderungen nicht,
und ein Restore warnt nicht, wenn sich ein Zeiger seit dem Eintrag weiterbewegt hat (ADR-013).
\item Eine dauerhafte Liste der entfernten Blobs, die \type{track} und \type{status} prüfen,
und ein Befehl, der die ID eines Blobs zu einem Pfad nennt, fehlen;
ein Blob mit beschädigter Datei lässt sich nicht purgen (ADR-014).
\stopitemize

Kapitel~11 sammelt diese Punkte mit den offenen Fragen der späteren Phasen.
