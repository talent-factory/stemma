\chapter{Architektur}

Dieses Kapitel beschreibt die Schichten des Systems und die Verteilung der Verantwortung.
Es setzt die Entscheidungen aus ADR-002 und ADR-003 um.

\section{Schichtenmodell}

Der Kern enthält die gesamte Logik:
Objektspeicher, Referenzen, Operation Log, Arbeitskopie und Autorisierung,
später auch Diff und Merge.
Er liegt in einer eigenen Bibliothek (\type{stemma-core}).
Alle Oberflächen rufen denselben Kern auf (\in{Abbildung}[fig:layers]).
In Phase 1 gibt es eine Oberfläche, die Kommandozeile (\type{stemma-cli})
mit Befehlen wie \type{init}, \type{commit} und \type{op log}.
Ein API-Server für Hub und Clients folgt in Phase 5,
ein MCP-Server als Adapter für Agenten in Phase 6.

Prüfungen gehören in den Kern, nicht in die Adapter. Ein Aufruf über die CLI,
die API oder den MCP-Server muss dieselbe Entscheidung erhalten.

\section{Akteure}

Jede Operation, die ein Repository ändert oder eine Änderung plant, hat einen Akteur (ADR-002).
Ein Mensch wird durch seine Kennung beschrieben.
Ein Agent führt zusätzlich Modellversion, Session und einen auftraggebenden Menschen mit,
den Sponsor.
Der Sponsor verantwortet die Handlungen des Agenten.
Jeder Commit und jeder Eintrag des Operation Logs nennt seinen Akteur in derselben Form,
einer Zeile wie \type{human daniel} (\in{Abbildung}[fig:actors]).

\startplacefigure[title={Akteur: Mensch oder Agent mit Sponsor},
    reference=fig:actors,location=here]
\externalfigure[images/actors.pdf][width=0.9\textwidth]
\stopplacefigure

Die Kommandozeile liest den Akteur aus der Option \type{--actor}
oder der Umgebungsvariablen \type{STEMMA_ACTOR}
und kennt keinen Standardwert,
damit ein Agent nie stillschweigend als Mensch auftritt.
Geprüft wird nur, ob die Zeile den Regeln für Akteure entspricht.
Sie belegt nicht, wer einen Befehl wirklich ausführt;
das sollen später Signaturen leisten (ADR-003, ADR-004).

\section{Autorisierung}

Bei jeder solchen Operation fragt der Kern,
ob der Akteur sie am Ziel ausführen darf (\type{authorize(actor, operation, target)}).
Das gilt auch für einen Plan wie \type{purge} ohne \type{--apply},
denn er liest, was die Änderung berühren würde.
Die Befehle, die nur das Log lesen (\type{op log}, \type{op verify}),
haben keinen Akteur und fragen nicht.
In Phase 1 erlaubt die Prüfung alles.
Nur einen Purge verweigert der Kern einem Agenten schon vorher, fest im Code (ADR-014).
Die Frage ist trotzdem Pflicht,
damit spätere Regeln ohne Umbau des Kerns eingeführt werden können.

\section{Ort der Berechtigungen}

Rollen und Policies liegen auf dem Server und werden dort durchgesetzt. Eine Regel steht fest
im Kern: Nur ein Mensch darf einen Purge machen, denn er lässt sich nicht rückgängig machen
(ADR-002, ADR-014).
Signaturen von Commits und Freigaben liegen im Repository und lassen sich unabhängig vom Server
prüfen. Die Policy-Dateien sind pro Namespace und selbst Stufe 3 aus ADR-004.
